| PM6 | 🐞 **SECURITY — a caller declaring a role marks it as owned by the seeding pass.** | 📋 | P2 — `permissions.md` says a role is marked `seeded` when a seeding pass writes it through `SetActions`, and `AddAction`/`RemoveAction` then refuse it; nothing stops a hand-made role arriving already marked. **Did**: mounted `routes.Routes(pm)` over a real manager on the in-memory harness (`wakala.permissions.json`), `POST /permissions/roles {"code":"writer","name":"Writer","seeded":true}`, then `POST /permissions/roles/writer/actions {"action":"catalog.entry.upsert"}`. **Observed**: `201 {"code":"writer","name":"Writer","seeded":true,"created_at":"2026-09-28T08:27:03.435354724Z",…,"deleted":false}`, then `409 {"error":"permissions: a seeded role's actions are owned by the seeding pass"}`; `GET /permissions/roles?seeded=true` lists it. `CreateRole` resets `created_at`, `updated_at` and `deleted` but never `Seeded`, and `create_role` binds the whole body. **Threat**: whoever holds `permissions.role.create` makes a bundle read as deployment-owned — a review filtering `seeded=true` counts it among the seeding pass's roles, and holders of `role_action.create`/`.delete` are refused on it, so its list can only change through a whole-list replace. It grants nothing by itself. **Control**: none; the PM5 fix (fab0482) moved `granted_by` to the caller and its own close note names this field as the same class, left open. **Verdict**: real on the module's own route table; unmounted, hence P2, the same grade PM5 carried. Red test (intentional, leave red until fixed): `routes/role_seeded_security_test.go`'s `TestPM6_OpenHole_CreateRoleTakesSeededFromTheRequestBody`, which today prints `PM6 (P2) open hole: a role created by hand reads seeded=true because the request body said so…` and `…adding an action to a hand-made role answered 409 …, want 201`. Found 2026-09-28 by the scheduled security sweep. **Second door, same outcome (2026-09-29, twenty-fourth sweep)**: `PUT /permissions/roles/writer/actions {"actions":["catalog.entry.upsert","permissions.grant.create"]}` on a hand-made role (`seeded:false`) → `200`, then `GET /permissions/roles/writer` → `"seeded":true`, `GET /permissions/roles?seeded=true` lists it, and `POST …/actions {"action":"catalog.entry.open"}` → `409 {"error":"permissions: a seeded role's actions are owned by the seeding pass"}`. `set_actions` exposes `SetActions` — the seeding pass's own write, which sets `Seeded` — to any `permissions.role_action.replace` holder, so stopping `CreateRole` taking `seeded` from the body leaves this path open; the fix has to decide whether the route may mark a role seeded at all. Not a separate row: one field, one threat, one owner decision. |
| PM7 | 🐞 **BUG — `ListRoles`' `name` filter treats the caller's search text as a raw SQL `LIKE` pattern, so a literal `_` or `%` in the search over- or under-matches instead of narrowing the list.** | 📋 | `role.go`'s `ListRoles` builds `"lower("+columnName("Name")+") like ?", "%"+lower(f.Name)+"%"` straight from `f.Name` with no escaping of `LIKE`'s own wildcard characters — the same loophole class `mwanachama-backend-agency`'s AG32 already fixed across all 17 of that repo's `List<Type>` filters (`likeFilter` there now escapes `%`/`_` before building the pattern), not yet applied here. **Demonstrated** against a real `PermissionsManager` (sqlite, the shipped `spec/examples/wakala.permissions.json` spec, `newTestManager`): seeded three roles named `AlphaXBeta`, `Gamma Reader`, `Delta Writer`, then `ListRoles(RoleFilter{Name: "Alpha_Beta"})` — a caller searching for the literal substring `"Alpha_Beta"` — **returned 1 role, `AlphaXBeta`**, a false-positive match because the unescaped `_` matches any single character; `ListRoles(RoleFilter{Name: "_"})` — a one-character search term that should narrow the list — **returned all 3 of 3 roles**, because every non-empty name contains at least one character for `_` to match. Both are wrong in opposite directions: a real name containing `_` or `%` is missed or over-matched, and a search term containing `_` or `%` widens rather than narrows. **Threat model**: correctness only, not security — `permissions.role.list` is already gated like every other action here, and the filter only ever narrows or widens *readable* rows the caller could already list unfiltered; the scheduled security sweep looked at this exact shape (`documentation/4. qa/security-sweeps/mwanachama-backend-permissions.md`'s lead (1b)) and ruled it a correctness row for this board, not a hole. **Fix location**: `role.go`'s `ListRoles`, escaping `%`/`_` (and the escape character itself) in `f.Name` before building the `LIKE` pattern — the same `likeFilter` shape AG32 already ships in the sibling repo. **Verdict**: open. Red test: `TestPM7_OpenBug_NameFilterTreatsUnderscoreAndPercentAsWildcards` in this package's own `permissions_test.go`, which today prints both wrong counts quoted above. Found 2026-09-29 by the scheduled integration-test sweep, widening AG32's loophole class into this sibling repo. |
| PM8 | 🐞 **BUG — `ListRoles` and `ListGrants` have no default cap, so a caller who names no limit gets the whole live table back in one response.** | 📋 | `role.go`'s `ListRoles` and `grant.go`'s `ListGrants` each hand-roll their own query (`q.Order(...).Find(&rows)` / `q.Find(&rows)`) and neither ever calls `.Limit(...)` — confirmed by `grep -n "\.Limit(" *.go` outside tests, empty. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`): seeded 150 roles, `ListRoles(RoleFilter{})` returned all 150; seeded one role plus 150 grants against it, `ListGrants(GrantFilter{})` returned all 150. This module builds its `List*` methods by hand rather than through `mwanachama-backend-shared/specstore.List` (unlike `mwanachama-backend-agency`'s `list[T]` wrapper), so it does **not** inherit the fix filed as that engine's `S24` — this is the same loophole class (also `mwanachama-backend-catalog`'s CAT10, `mwanachama-wakala-api`'s WK36 against `mwanachama-backend-agency`) landing independently in this repo's own hand-rolled query code, and needs its own fix here regardless of what S24 does. **Fix location**: `role.go`'s `ListRoles` and `grant.go`'s `ListGrants`, a default `.Limit(...)` when the caller's filter carries none. Red test: `TestPM8_OpenBug_ListRolesHasNoDefaultCap` / `TestPM8_OpenBug_ListGrantsHasNoDefaultCap` in this package's own `list_cap_test.go`, printing the counts quoted above. Found 2026-09-29 by the scheduled integration-test sweep, widening CAT10/S24's loophole class into this sibling repo. |
| PM9 | 🐞 **BUG — `SetActions` fails with a raw database error instead of deduplicating when the caller's own action list repeats an entry.** | 📋 | `action.go`'s `SetActions` clears a role's existing `role_action` rows in a transaction, then inserts every entry of the caller's `actions` slice verbatim with no de-duplication — unlike `AddAction`'s `writeAction`, which checks `held > 0` before inserting so a repeated call is a no-op. `role_action`'s primary key is the pair `(role_code, action)` (`permissions.blueprint.json`), so a caller-supplied list that names the same action twice (a plausible shape: two overlapping declarations merged before the call, or a double-submitted form) hits that constraint on the second insert and the whole transaction rolls back. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`): `CreateRole(writer)` then `SetActions(ctx, "writer", []string{"catalog.entry.upsert", "catalog.entry.upsert"})` returned `permissions: set actions: constraint failed: UNIQUE constraint failed: agency_permissions_role_actions.role_code, agency_permissions_role_actions.action (1555)` and zero actions, where a caller asking to grant one action twice should end up with that one action granted once. The rollback is clean (no partial row, confirmed via `ListActions` reading back empty afterward) and the raw driver error never reaches an HTTP caller — `routes.go`'s sentinel table has no entry for it, so `dispatch.handlerFor` maps it to the opaque `internal error` 500 already confirmed by the security sweep's own masking pin — but the operation still fails outright on a request that should succeed, and the error string does leak the physical table name (`agency_permissions_role_actions`) to any direct Go caller of this library (this repo's own `mcp`/host code, once PM1 exists). **Fix location**: `action.go`'s `SetActions`, de-duplicating `actions` before the insert loop (or skipping a repeat the way `writeAction` already does). Red test: `TestPM9_OpenBug_SetActionsRejectsADuplicateActionInTheList` in this package's own `action_setactions_test.go`, printing the constraint error quoted above. Found 2026-09-29 by the scheduled integration-test sweep, widening the idempotency loophole catalogue entry into this repo's one bulk-replace operation. |
| PM10 | 🐞 **BUG — `CreateGrant` accepts a role code that has already been retired, so a caller can mint a brand-new grant that `MayPerform` will silently deny forever.** | 📋 | `grant.go`'s `CreateGrant` calls `findRole(ctx, g.RoleCode)` only to prove the code exists; `findRole` (`role.go:40`) queries by `Code` alone with no `Deleted` filter, so a role that `DeleteRole` has soft-deleted (`Deleted: true`) is still "found" and the grant is created. `MayPerform`/`ActionsFor`/`ActionsAnywhere` (`permissions_manager.go:74,105,134`) each join `roleRole` with `Where("r."+columnName("Deleted")+" = false")`, so the new grant confers nothing from the moment it is created — but `ListGrants` filters only on the grant's own `Deleted` column, so it reads back as an ordinary live grant (`Deleted:false`) with no indication its role is dead. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`, `spec/examples/wakala.permissions.json`): `CreateRole(writer)` → `AddAction(writer, "catalog.entry.upsert")` → `DeleteRole(writer)`, then `CreateGrant({Subject:"bob",Scope:"instance:abc",RoleCode:"writer"})` returned `{Subject:bob Scope:instance:abc RoleCode:writer Deleted:false}` with `err=nil`; `ListGrants(GrantFilter{Subject:"bob"})` reads back that same row as the only, apparently-live grant; `MayPerform(ctx,"bob","instance:abc","catalog.entry.upsert")` answers `false`. The existing `routes/retired_role_edit_security_test.go` only covers *editing* an already-held grant/role after retirement (and treats that as allowed-but-inert by design); it never exercises creating a **new** grant against an already-retired role code, which is the gap this row closes. **Fix location**: `grant.go`'s `CreateGrant`, refusing (e.g. reusing `ErrRoleNotFound`, or a new `ErrRoleRetired`) when `findRole` returns a role with `Deleted: true` — the same way it already refuses a code nobody ever created. Red test: `TestPM10_OpenBug_CreateGrantAcceptsARetiredRole` in this package's own `grant_retired_role_test.go`, printing the grant quoted above. Found 2026-09-30 by the scheduled integration-test sweep, reading `grant.go`/`role.go`/`permissions_manager.go` end to end for this run's deepening pass. |
