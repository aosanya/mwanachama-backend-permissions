| PM2 | 🧪 **No Postgres integration test.** | 📋 | Everything runs on SQLite today. Catalog carries `postgres_integration_test.go`, overriding `Instance` to a random `pg<hex>` per run so it cannot touch a real deployment — copy that discipline, not just the file. The case that matters here is `MayPerform`'s three-way join under a real planner, and the composite primary keys, which SQLite is laxer about. |
| PM4 | 🔒 **A grant's scope is validated; a role's actions are not checked against anything real.** | 📋 | `isAction` proves an action is well-formed, never that it exists. A typo (`agency.module.lst`) is stored happily and silently permits nothing, which is the failure mode hardest to notice. The seeding pass (`DSN-1735`) makes this mostly moot for seeded roles, but a hand-made role can still hold a permission for an action nobody declares. Options: refuse unknown actions at write time, which needs the module to be told the declared set; or a report that lists permissions matching no declared action, which keeps this module ignorant and is probably the right shape. |
| PM5 | 🐞 **SECURITY — a caller writing a grant records whoever it likes as the grantor.** | 📋 | P2 — the blueprint's `grant.granted_by` is "the subject that made this grant, for the trail", and nothing enforces it. **Did**: mounted `routes.Routes(pm)` over a real manager on the in-memory harness (`wakala.permissions.json`), `POST /permissions/roles {"code":"writer","name":"Writer"}` → 201, then `POST /permissions/grants {"subject":"mallory","scope":"module:catalog","role_code":"writer","granted_by":"root-admin","granted_at":"1999-01-01T00:00:00Z","deleted":true}`. **Observed**: `201 {"subject":"mallory","scope":"module:catalog","role_code":"writer","granted_by":"root-admin","granted_at":"2026-09-27T10:25:41.549043432Z","deleted":false}`, and `GET /permissions/grants?subject=mallory` reads `"granted_by":"root-admin"` back. `granted_at` and `deleted` are reset server-side; `granted_by` is stored verbatim because `create_grant` binds the whole body and `CreateGrant` never sets it. The same shape on `create_role`: `{"code":"reader","name":"Reader","seeded":true}` → 201 with `"seeded":true`, after which `POST /roles/reader/actions` answers `409 a seeded role's actions are owned by the seeding pass`. **Threat**: whoever holds `permissions.grant.create` can make any grant — including a self-grant — read as if another subject, or the bootstrap (`""`), made it, which is exactly the trail a revocation review reads. **Control**: none; the manager has no caller to record, since the dispatcher hands it only the bound body. **Verdict**: real on the module's own route table; not reachable in production yet because nothing mounts these routes (wakala-api consumes only `MayPerform`), hence P2 rather than P1. It becomes P1 the day a mount exposes `create_grant`. Red test (intentional, leave red until fixed): `routes/grant_security_test.go`'s `TestPM5_OpenHole_GrantedByIsTakenFromTheRequestBody`, which today prints `PM5 (P2) open hole: the stored grant's granted_by is "root-admin", the value the request body claimed`. Found 2026-09-27 by the scheduled security sweep. |
| PM6 | 🐞 **BUG — filtering grants by `role_code` over HTTP silently returns every role's grants.** | 📋 | `list_grants`'s query arg binds the whole query string onto `models.GrantFilter` (`dispatch`'s `wholeQuery`), which derives each query key from the lowercased Go field name, not the struct's `json` tag — unlike whole-*body* binding, which decodes through `encoding/json` and does respect the tag. `GrantFilter.RoleCode` therefore only binds on `?rolecode=`, never on `?role_code=`, even though `role_code` is the spelling every response body, every route path segment (`/roles/{role_code}/actions`) and the operation's own doc string use. **Did**: real `httptest.NewServer` over `routes.Routes(pm)` on the in-memory harness, created roles `writer`/`reader`, granted `alice` `writer` and `bob` `reader` in the same scope, then `GET /permissions/grants?role_code=writer`. **Observed**: `200` with both alice's and bob's grants — `?rolecode=writer` (undocumented, no underscore) correctly returns only alice's. **Impact**: an operator auditing "who holds `writer`" through the one documented spelling of the filter sees every subject's grants across every role, silently — no error, no truncation notice. Defect lives in `mwanachama-backend-shared/dispatch/dispatch.go`'s `queryKey` (used by `wholeQuery`); this module's `models.GrantFilter` is the field that trips it. A `mwanachama-backend-shared` follow-up row may be warranted since any other declared domain filtering a multi-word field through a whole-query arg has the same gap. Red test: `routes/grant_filter_bug_test.go`'s `TestPM6_OpenBug_ListGrantsIgnoresRoleCodeQueryParam`. Found 2026-09-27 by the scheduled integration-test sweep. |
| PM7 | 🐞 **BUG — `PUT` a role's actions with a body missing `actions` silently wipes and permanently locks the role.** | 📋 | `set_actions`'s body arg declares `"as": "actions", "required": true`, but `dispatch`'s `bind()` never enforces `Arg.Required` — a missing key just binds the Go zero value, here a nil `[]string`. `SetActions` treats that identically to an explicit `{"actions": []}`: it deletes every existing `role_action` row for the role inside its transaction and then unconditionally sets `seeded = true`, which is what makes it worse than a plain no-op — a seeded role's actions can never again be touched by `AddAction`/`RemoveAction` (`ErrSeededRole`), so there is no hand repair. **Did**: real `httptest.NewServer` over `routes.Routes(pm)`, created role `writer`, added `catalog.entry.read`, then `PUT /permissions/roles/writer/actions` with body `{}`. **Observed**: `200 []` — the action list is gone, and `GET /permissions/roles/writer` reads back `"seeded":true`; a follow-up `POST .../actions` to re-add the action answers `409 a seeded role's actions are owned by the seeding pass`. **Impact**: a client bug or a dropped field (not a malicious caller — this needs no privilege beyond whatever already permits `permissions.role_action.replace`) permanently strips a role down to zero permissions with no way back except another full `SetActions`/`Seed` call. A fix can live entirely in this module: `bind()`'s `reflect.Zero` for a missing slice key is Go's untyped `nil`, distinguishable from the non-nil empty slice `json.Unmarshal("[]", ...)` produces for an explicit `{"actions": []}` — `SetActions` can refuse `actions == nil` while still allowing an intentional empty list. Red test: `routes/setactions_bug_test.go`'s `TestPM7_OpenBug_SetActionsWithoutActionsFieldWipesAndLocksTheRole`. Found 2026-09-27 by the scheduled integration-test sweep. |
