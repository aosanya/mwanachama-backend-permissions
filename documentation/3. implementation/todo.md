| PM1 | 🔌 **MCP tools, the other half of catalog's shape.** | 📋 | `routes/tools.go` does not exist yet. Catalog's equivalent is what turns the declared operations into MCP tools with per-field prose, required-ness and read-only flags read from the blueprint (`routes.Fields()`, keyed by Go type), so a tool's schema and the column a write lands in cannot drift. The 14 operations and their errors are already declared, so this is `dispatch.Tools(s, deps)` plus the `Fields()` map and an `operatorOnly` equivalent — except that here nothing is anonymous, so the split is simpler than catalog's. |
| PM2 | 🧪 **No Postgres integration test.** | 📋 | Everything runs on SQLite today. Catalog carries `postgres_integration_test.go`, overriding `Instance` to a random `pg<hex>` per run so it cannot touch a real deployment — copy that discipline, not just the file. The case that matters here is `MayPerform`'s three-way join under a real planner, and the composite primary keys, which SQLite is laxer about. |
| PM4 | 🔒 **A grant's scope is validated; a role's actions are not checked against anything real.** | 📋 | `isAction` proves an action is well-formed, never that it exists. A typo (`agency.module.lst`) is stored happily and silently permits nothing, which is the failure mode hardest to notice. The seeding pass (`DSN-1735`) makes this mostly moot for seeded roles, but a hand-made role can still hold a permission for an action nobody declares. Options: refuse unknown actions at write time, which needs the module to be told the declared set; or a report that lists permissions matching no declared action, which keeps this module ignorant and is probably the right shape. |
| PM6 | 🐞 **SECURITY — a caller declaring a role marks it as owned by the seeding pass.** | 📋 | P2 — `permissions.md` says a role is marked `seeded` when a seeding pass writes it through `SetActions`, and `AddAction`/`RemoveAction` then refuse it; nothing stops a hand-made role arriving already marked. **Did**: mounted `routes.Routes(pm)` over a real manager on the in-memory harness (`wakala.permissions.json`), `POST /permissions/roles {"code":"writer","name":"Writer","seeded":true}`, then `POST /permissions/roles/writer/actions {"action":"catalog.entry.upsert"}`. **Observed**: `201 {"code":"writer","name":"Writer","seeded":true,"created_at":"2026-09-28T08:27:03.435354724Z",…,"deleted":false}`, then `409 {"error":"permissions: a seeded role's actions are owned by the seeding pass"}`; `GET /permissions/roles?seeded=true` lists it. `CreateRole` resets `created_at`, `updated_at` and `deleted` but never `Seeded`, and `create_role` binds the whole body. **Threat**: whoever holds `permissions.role.create` makes a bundle read as deployment-owned — a review filtering `seeded=true` counts it among the seeding pass's roles, and holders of `role_action.create`/`.delete` are refused on it, so its list can only change through a whole-list replace. It grants nothing by itself. **Control**: none; the PM5 fix (fab0482) moved `granted_by` to the caller and its own close note names this field as the same class, left open. **Verdict**: real on the module's own route table; unmounted, hence P2, the same grade PM5 carried. Red test (intentional, leave red until fixed): `routes/role_seeded_security_test.go`'s `TestPM6_OpenHole_CreateRoleTakesSeededFromTheRequestBody`, which today prints `PM6 (P2) open hole: a role created by hand reads seeded=true because the request body said so…` and `…adding an action to a hand-made role answered 409 …, want 201`. Found 2026-09-28 by the scheduled security sweep. |
