| PM2 | 🧪 **No Postgres integration test.** | 📋 | Everything runs on SQLite today. The case that matters here is `MayPerform`'s three-way join under a real planner, and the composite primary keys, which SQLite is laxer about. |
| PM4 | 🔒 **A grant's scope is validated; a role's actions are not checked against anything real.** | 📋 | `isAction` proves an action is well-formed, never that it exists. A typo (`agency.module.lst`) is stored happily and silently permits nothing, which is the failure mode hardest to notice. The seeding pass (`DSN-1735`) makes this mostly moot for seeded roles, but a hand-made role can still hold a permission for an action nobody declares. Options: refuse unknown actions at write time, which needs the module to be told the declared set; or a report that lists permissions matching no declared action, which keeps this module ignorant and is probably the right shape. |
| PM14 | 🐞 **SECURITY — a role-replace request that names no actions list strips every action from the role, so each subject holding it silently loses every permission it carried.** | 🚀 | P2 — `permissions.operations.json` declares `set_actions`' body argument `actions` `"required": true`; the module declares no MCP tools, so REST is its only door, and that door does not enforce it. **Did** (2026-10-05, in-memory sqlite harness, `routes.Routes(pm)` over a real manager on `wakala.permissions.json`): `POST /permissions/roles {"code":"owner","name":"Owner"}`, `PUT /permissions/roles/owner/actions {"actions":["permissions.grant.create","permissions.role.update","permissions.role_action.update"]}`, `POST /permissions/grants {"subject":"alice","scope":"*","role_code":"owner"}`, `GET /permissions/check?subject=alice&scope=*&action=permissions.grant.create`, then `PUT /permissions/roles/owner/actions {"action":["permissions.grant.create"]}` (the key misspelled) and the same check again. **Observed**: the first check `200 true`; the misspelled replace `200 []`; `GET /permissions/roles/owner/actions` `200 []`; the second check `200 false`. `{}` and `{"actions":null}` answer the same `200 []`. An empty body is refused (`400 the request body is not a JSON object`), and so is `[]`/`"x"` on `create_role`, so only a JSON object lacking the key gets through. **Threat**: any holder of `permissions.role_action.replace`, through a typo, a stale client or a body built for another version, empties a bundle with nothing to say it happened. Every subject holding that role loses every action at once. If the role is the one that administers grants, nobody is left who can put it back through this module. The intended clear, `{"actions":[]}`, cannot be told apart from a mistake afterwards. **Control**: none. The dispatcher's `bindOne` binds an absent body key to the zero value (`nil`) and never reads `required` on HTTP; that class is shared's S35, paused on the owner's choice between enforcing `required` and option (c), each module refusing for itself. `SetActions` takes option (c) for nothing: a nil list deletes every `role_action` row for the code and inserts none. A `nil` from JSON is distinguishable from `[]`, so the module can refuse it without waiting on S35. See Go-SCP [Input Validation](../../../developer/.claude/skills/security-gap-hunt/references/owasp-go-scp/src/input-validation/validation.md). **Verdict**: real on the module's own route table; unmounted in wakala-api today (`buildPermissions` needs `PERMISSIONS_DATABASE_URL`), so not yet reachable in production. Red test: `routes/set_actions_absent_list_security_test.go`'s `TestPM14_OpenHole_ReplaceWithNoActionsKeyStripsEveryActionFromTheRole`. Found by the security sweep. |
| PM15 | 🐞 **BUG — `ListRoles` returns roles in the opposite order from what `permissions.operations.json` declares, oldest first rather than newest first.** | 🚀 | `permissions.operations.json`'s `list_roles` operation carries the description `"List the bundles declared here, newest naming first."`, but `role.go`'s `ListRoles` builds its query with `.Order(columnName("Code"))` — a plain ascending sort on the caller-supplied `Code` (never auto-minted; `CreateRole` takes it verbatim from the request body), with no ordering by `created_at`/`updated_at` at all. The declared "newest first" claim has no implementation behind it in either sense: not newest-first by time, and not even consistently related to creation order, since `Code` is an arbitrary caller-chosen string. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`, the shipped `spec/examples/wakala.permissions.json` spec): `CreateRole(code="a_older")` then `CreateRole(code="b_newer")`, then `ListRoles(RoleFilter{})` returned `[a_older, b_newer]` — the role created first listed first, exactly the reverse of what the declared "newest naming first" order promises a caller. Flagged as an unfiled lead across several prior sweeps ("still needs an owner call, still not filed") rather than filed, but the drift is now concretely demonstrated, which is the evidence bar this board's own filing rule asks for — this is catalogue entry 12 (declared-vs-implemented drift) on a declared operation's own behaviour claim, not merely thin prose. **Fix location**: `role.go`'s `ListRoles` — either order by `columnName("UpdatedAt")`/`columnName("CreatedAt")` descending to match the declared behaviour, or correct the operation's own description to say what the code actually does; either is a decision for the module owner, not this sweep, which never edits `permissions.operations.json` or `role.go`. Red test: `TestPM15_OpenBug_ListRolesIgnoresDeclaredNewestFirstOrder` in this package's own `list_order_test.go`, printing the reversed order quoted above. Found 2026-10-05 by the scheduled integration-test sweep. |
| PM16 | 🐞 **BUG — `ListActions` has no default cap, the same loophole class already filed as PM8 against `ListRoles`/`ListGrants`, landing a third time in this repo's own hand-rolled `List*` family.** | 🚀 | `action.go`'s `ListActions` builds `.Order(columnName("Action")).Find(&rows)` with no `.Limit(...)` anywhere, same as `ListRoles`/`ListGrants` before PM8 — `grep -n "\.Limit(" *.go` outside tests is still empty. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`, the shipped `spec/examples/wakala.permissions.json`): `CreateRole(writer)`, then 150 `AddAction(writer, "module_NNN.thing.do")` calls with 150 distinct action strings (`isAction` imposes no count limit on a role, only a shape on each string), then `ListActions(ctx, "writer")` returned all 150 of 150. A role's action set is exactly as unbounded as the role table or grant table PM8 already covers — `AddAction` has no cap on how many distinct actions one role may hold — so the same caller-controls-the-response-size shape applies: a role with enough actions added to it makes every future `ListActions` call (and any admin screen built on it) answer with an unbounded body. **Fix location**: `action.go`'s `ListActions`, a default `.Limit(...)` matching whatever PM8 lands on for `ListRoles`/`ListGrants` — the three should likely share one fix rather than three independent ones. Red test: `TestPM16_OpenBug_ListActionsHasNoDefaultCap` in this package's own `list_cap_test.go`, printing the count quoted above. Found 2026-10-07 by the scheduled integration-test sweep, widening PM8's own loophole class to this repo's third `List*` method. |
| PM18 | 🐞 **BUG — `DeleteRole` can permanently destroy a role the seeding pass marked `Seeded`, even though every other write to that role's content is already refused.** | 🚀 | `action.go`'s `AddAction`/`RemoveAction` both check `role.Seeded` and refuse with `ErrSeededRole` — `permissions.md` says a seeded role's actions "are owned by the seeding pass," so an ordinary caller cannot touch them. `role.go`'s `DeleteRole` runs no such check at all: it looks the role up, then unconditionally marks it `Deleted: true`. Because this module's own retired-code behaviour is permanent by design (`CreateRole` refuses any code `findRole` can see regardless of its `Deleted` flag, confirmed in `routes/retired_code_reuse_security_test.go`), and because re-running the seeding pass against a dead row is inert by the same already-established "editing a retired role never revives it" rule (`routes/retired_role_edit_security_test.go`), deleting a seeded role is **irreversible**: the seeding pass itself can never reconstitute the role it declared under that exact code on a later boot. **Demonstrated** against a real `PermissionsManager` (sqlite, `newTestManager`, the shipped `spec/examples/wakala.permissions.json`): `CreateRole(writer)` → `SetActions(writer, ["catalog.entry.upsert"])` (`role.Seeded` reads `true`, confirmed; `AddAction(writer, "permissions.grant.create")` is refused as expected) → `DeleteRole(ctx, "writer")` answered `nil` (success) — real output: `PM18 open bug: DeleteRole("writer") on a seeded role answered nil (success); want it refused the same way AddAction/RemoveAction already refuse any hand write to a role the seeding pass owns`. Afterward `GetRole("writer")` reads `Deleted:true`, and `CreateRole(Role{Code:"writer"})` answers `permissions: that role code is taken` forever — real output: `PM18 open bug: a caller holding only permissions.role.delete permanently destroyed role "writer", which the seeding pass marked Seeded=true and which AddAction/RemoveAction already refuse to touch (DeleteRole err=<nil>); CreateRole("writer") now answers permissions: that role code is taken forever, so the seeding pass itself can never reconstitute the role it declared under this code again`. **Threat**: any caller holding only `permissions.role.delete` — a far narrower grant than `role_action.delete`/`.update`, which are the ones `Seeded` is meant to defend against — can permanently end a deployment-managed role with one call, and nothing about the module, the seeding pass, or a later boot can ever bring that exact code back. **Widened and ruled out**: `Seeded` is unique to this module (`grep -rln Seeded --include=*.go` across `mwanachama-backend-agency`/`-catalog`/`-shared`/`mwanachama-wakala-api`, outside test files, empty) — there is no sibling-repo instance of this exact shape to widen into. **Fix location**: `role.go`'s `DeleteRole`, checking `role.Seeded` the same way `AddAction`/`RemoveAction` already do, and refusing with `ErrSeededRole` (or a role-owner decision on whether the seeding pass itself should be allowed to retire its own roles through some other path). Red test: `TestPM18_OpenBug_DeleteRoleDestroysASeededRoleForever` in this package's own new `delete_seeded_role_test.go`, printing the output quoted above. `go test ./...`/`-tags=integration ./...` otherwise unchanged (same fourteen pre-existing reds); `gofmt -l .`/`go vet ./...` clean; no product code touched. Found 2026-10-10 by the scheduled integration-test sweep, widening `AddAction`/`RemoveAction`'s own `Seeded` guard into the one write path that lacked it. |
