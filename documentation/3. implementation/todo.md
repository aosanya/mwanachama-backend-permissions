| PM1 | 🔌 **MCP tools, the other half of catalog's shape.** | 📋 | `routes/tools.go` does not exist yet. Catalog's equivalent is what turns the declared operations into MCP tools with per-field prose, required-ness and read-only flags read from the blueprint (`routes.Fields()`, keyed by Go type), so a tool's schema and the column a write lands in cannot drift. The 14 operations and their errors are already declared, so this is `dispatch.Tools(s, deps)` plus the `Fields()` map and an `operatorOnly` equivalent — except that here nothing is anonymous, so the split is simpler than catalog's. |
| PM2 | 🧪 **No Postgres integration test.** | 📋 | Everything runs on SQLite today. Catalog carries `postgres_integration_test.go`, overriding `Instance` to a random `pg<hex>` per run so it cannot touch a real deployment — copy that discipline, not just the file. The case that matters here is `MayPerform`'s three-way join under a real planner, and the composite primary keys, which SQLite is laxer about. |
| PM4 | 🔒 **A grant's scope is validated; a role's actions are not checked against anything real.** | 📋 | `isAction` proves an action is well-formed, never that it exists. A typo (`agency.module.lst`) is stored happily and silently permits nothing, which is the failure mode hardest to notice. The seeding pass (`DSN-1735`) makes this mostly moot for seeded roles, but a hand-made role can still hold a permission for an action nobody declares. Options: refuse unknown actions at write time, which needs the module to be told the declared set; or a report that lists permissions matching no declared action, which keeps this module ignorant and is probably the right shape. |
| PM5 | 🐞 **SECURITY — a subject allowed to grant in one scope grants itself any role in `*` or any other scope.** P1. | 📋 | **Did**: drove this module's own declared operations through `mwanachama-backend-shared/dispatch` with its new `Deps.Authorize` (3fdfd6e) wired the obvious way a mount would — `MayPerform(caller, "instance:a", action)` — on the in-memory harness. `mallory` holds role `granter` (`permissions.grant.create` only) in `instance:a`; role `admin` lists `agency.goal.delete`. As mallory: `POST /grants {"subject":"mallory","scope":"*","role_code":"admin"}`. **Observed**: `201 {"subject":"mallory","scope":"*","role_code":"admin","granted_at":"2026-09-27T10:14:25…","deleted":false}`; `MayPerform(mallory, instance:b, agency.goal.delete)` went `false` → `true`. `scope: "instance:b"` is accepted the same way. The same caller's `POST /roles/admin/actions` was correctly refused `403`, so the gate is live — it just cannot see the body. **Threat**: once mounted (DSN-1736), anyone delegated grant rights over one agency escalates to every agency, and the self-made grant carries an empty `granted_by`, which the blueprint says reads as a bootstrap. **Control**: the authorizer is `func(ctx, action) error` — it never sees the grant's `scope` or `role_code`, and `CreateGrant` checks neither against the granter. The design doc's "the module gates itself" holds only for the action, not for where it is exercised. A fix belongs either here (`CreateGrant`/`WithdrawGrant` require the granter to hold `permissions.grant.create` in the target scope, or `*`) or in `dispatch` (hand bound arguments to the authorizer); decide which before mounting. **Verdict**: open. wakala-api mounted this module on 2026-09-27 (e31223e) only as the catalog's `MayPerform` gate — its `/grants` routes are not exposed there, so no production door reaches it today, but it is this domain's own stated boundary and it fails through the shared engine's own gate. Red test: `routes/routes_security_test.go` `TestPM5_OpenHole_AGranterScopedToOneInstanceGrantsItselfEverywhere`. |
| PM6 | 🐞 **SECURITY — a caller writes whatever `granted_by` it likes onto a grant, forging the audit trail.** P1. | 📋 | **Did**: in-memory harness, this module's `routes.Routes`: `POST /grants {"subject":"alice","scope":"instance:a","role_code":"editor","granted_by":"the-real-owner","granted_at":"1999-01-01T00:00:00Z"}`, then `GET /grants?subject=alice`. **Observed**: `201 {…,"granted_by":"the-real-owner","granted_at":"2026-09-27T10:14:14…"}` and the listing returns the same — `granted_at` is overwritten by the server, `granted_by` is stored verbatim. **Threat**: the blueprint calls `granted_by` "the subject that made this grant, for the trail"; any caller holding `permissions.grant.create` can attribute its grant to someone else, or leave it empty to pass as a bootstrap grant (see PM5). **Control**: `create_grant` binds the whole body (`{"from":"body","whole":true}`) and `CreateGrant`/`reinstate` copy `g.GrantedBy` unchanged. The granter should come from the authenticated caller on the context, with the body field refused or ignored. **Verdict**: open, client-set actor field. Red test: `routes/routes_security_test.go` `TestPM6_OpenHole_GrantedByIsTakenFromTheRequestBody`. |
| PM7 | 🐞 **SECURITY — a caller creates a role already marked `seeded`, claiming the seeding pass owns it.** P3. | 📋 | **Did**: `POST /roles {"code":"hand","name":"Hand","seeded":true,"created_at":"1999-01-01T00:00:00Z"}`, then `POST /roles/hand/actions {"action":"agency.goal.create"}`. **Observed**: `201 {…,"seeded":true,"created_at":"2026-09-27T10:14:14…"}` (clock overwritten, `seeded` kept), then `409 {"error":"permissions: a seeded role's actions are owned by the seeding pass"}`. **Threat**: low — a hand-made role is frozen against `AddAction`/`RemoveAction` and listed as seeded, so `ListRoles?seeded=` no longer tells an auditor which bundles a seeding pass computed. No path to more access was shown. **Control**: `create_role` binds the whole body and `CreateRole` resets `CreatedAt`/`UpdatedAt`/`Deleted` but not `Seeded`; only `SetActions`/`Seed` should set it. **Verdict**: open, hardening. Red test: `routes/routes_security_test.go` `TestPM7_OpenHole_SeededIsTakenFromTheRequestBody`. |
| PM8 | 🐞 **SECURITY — `GET /grants` returns every grant in one response, whatever `limit` the caller asks for.** P3. | 📋 | **Did**: planted 1200 grants on the in-memory harness, then `GET /grants?limit=5`. **Observed**: `200`, all 1200 rows, 137,865 bytes (1502 rows / 168,519 bytes in the exploratory probe). **Threat**: a caller holding `permissions.grant.list` pulls the whole table on every call — the table `MayPerform` reads on every gated request, so its size grows with every subject and scope. Same shape as `mwanachama-backend-catalog`'s CAT10 and wakala-api's WK36. **Control**: `ListGrants`/`ListRoles`/`ListActions` apply no `.Limit`; `models.GrantFilter` has no limit field, so `?limit=` is silently ignored. **Verdict**: open, cost. Red test: `routes/routes_security_test.go` `TestPM8_OpenHole_GrantListingHasNoCap`. |
